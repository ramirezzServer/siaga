# 0015. OpenTelemetry di ingest dan geo-processor, dan dashboard pipa data

Tanggal: 2026-09-25 · Status: diterima

## Konteks

Dokumen arsitektur menetapkan semua layanan diinstrumentasi OpenTelemetry (trace, metrik, log terstruktur) dengan trace ID ikut di event NATS, supaya satu gempa bisa dilacak dari polling sampai notifikasi dalam satu tampilan trace. Dashboard Grafana harus menampilkan kesehatan tiap sumber data (terlambat, galat, kuota tersisa), antrean NATS, dan query lambat PostgreSQL; target demo fase 1 adalah dashboard berisi data live semua sumber. PRD mengukur T1 (p95 < 10 detik dari data terdeteksi sampai notifikasi) dengan trace OpenTelemetry. Tujuan produksi adalah Grafana Cloud free tier; biaya harus tetap Rp0.

Sampai fase 1e-1, kesehatan hanya terlihat di `/status` JSON tiap layanan, `docs/events.md` sudah menyediakan header `traceparent` tetapi belum diisi, dan pesan `hazard.*` diterbitkan relay outbox di goroutine lain sehingga konteks pemrosesan pesan `raw.*` penyebabnya hilang.

Fase 1e-2 dipecah dua: **1e-2a** (ADR ini) instrumentasi dan dashboard; **1e-2b** Dockerfile, manifest Kubernetes, OTel Collector di cluster, Secret SOPS, retensi dan backup arsip.

## Keputusan

1. **SDK OpenTelemetry Go, konfigurasi dari environment standar.** Paket `libs/go/platform/otelx` memasang propagator W3C (`tracecontext`, `baggage`), lalu tracer, meter, dan logger provider OTLP/HTTP (`http/protobuf`) hanya untuk sinyal yang punya endpoint (`OTEL_EXPORTER_OTLP_ENDPOINT` atau `OTEL_EXPORTER_OTLP_{TRACES,METRICS,LOGS}_ENDPOINT`), dan menghormati `OTEL_SDK_DISABLED`, `OTEL_*_EXPORTER=none`, `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_TRACES_SAMPLER`, dan `OTEL_METRIC_EXPORT_INTERVAL`. gRPC ditolak saat start karena hanya exporter HTTP yang di-link. Tanpa endpoint tidak ada SDK yang terpasang (tracer dan meter noop, tanpa biaya), tetapi propagator tetap aktif sehingga `traceparent` pesan masuk tetap diteruskan ke pesan keluar. Resource: `service.name`, `service.namespace=siaga` (label `job` di Prometheus menjadi `siaga/<layanan>`), `service.version` (dari `-ldflags` saat build image, `dev` di lokal), `service.instance.id`, `deployment.environment.name` (`SIAGA_ENV`, bawaan `lokal`). Metrik runtime Go (`go.memory.*`, `go.goroutine.count`) dari `contrib/instrumentation/runtime`. Galat ekspor dicatat ke log paling sering sekali per menit per pesan.
2. **Log tetap JSON di stderr, ditambah OTLP.** `logx.New` menerima handler tambahan (bridge `otelslog`) dan menulis `trace_id`/`span_id` bila log dicatat dengan context yang membawa span. Log ke stderr tidak pernah dimatikan, supaya `make ingest`, `kubectl logs`, dan Loki menampilkan baris yang sama.
3. **Trace melintasi NATS lewat header, dan melintasi outbox lewat kolom.** `natsx.StartPublish` (span producer `send <subjek>`) menulis `traceparent` ke header setiap pesan; `natsx.StartProcess` (span consumer `process <subjek>`) melanjutkannya di consumer. Pesan `hazard.*` ditulis ke outbox di dalam span pemrosesan, jadi adapter PostgreSQL menyimpan `traceparent` dari context di kolom baru `hazard.outbox.traceparent` (migrasi 00006); relay meneruskannya lewat header, dan publisher membuat span penerbitan sebagai anaknya. Hasilnya satu trace per gempa: `poll bmkg-autogempa` → `GET` → `archive put` → `send raw.quake.bmkg` → `process raw.quake.bmkg` → query PostgreSQL → `INSERT hazard.outbox` → `send hazard.quake.created` (uji `TestTraceFromRawToHazard`). Bentuk `traceparent` dijaga dua kali, di `otelx.ValidTraceParent` dan constraint `outbox_traceparent_format` (versi 00, ID bukan nol, flag 00–03); nilai tidak sah dibuang, bukan menggagalkan transaksi. Konteks trace sengaja tidak dikirim ke sumber pihak ketiga (BMKG, USGS, Open-Meteo, OpenAQ, FIRMS).
4. **Use case tetap tanpa OpenTelemetry.** `internal/domain` dan `internal/app` tidak mengimpor paket OTel. Runner menerima `runner.PollObserver` dan sapuan menerima `sweep.ItemObserver` (context masuk, fungsi selesai dengan hasilnya), relay menerima `relay.Observer`; adapter `telemetry` tiap layanan mengisinya dengan span dan metrik. Fetcher dan arsip dibungkus dekorator di adapter yang sama. Span NATS ada di adapter `jspub` dan `natsjs`, span query di adapter `postgres` (`pgx.QueryTracer`).
5. **Metrik dibaca dari statistik yang sudah ada bila bisa.** Gauge dan counter kumulatif (umur data per konektor, kegagalan beruntun, record terbit/ditolak, sisa anggaran request, progres sapuan, pesan per consumer, perubahan kejadian, isi outbox, antrean consumer dan isi stream JetStream) dihitung dari snapshot saat metrik dikumpulkan (callback), tanpa pencatatan tambahan di jalur panas. Histogram dicatat di tempat kejadiannya dengan bucket detik yang ditetapkan sendiri. Nama mengikuti konvensi semantik bila ada (`http.client.request.duration`, `messaging.process.duration`, `db.client.operation.duration`), sisanya berawalan `siaga.`; atribut berkardinalitas rendah saja (nama konektor, anggaran, consumer, subjek, host, ringkasan query). Daftar lengkap nama Prometheus-nya (setelah diterjemahkan dari OTLP) ada di bagian Metrik di bawah.
6. **Latensi pipa diukur tanpa membuka isi pesan.** Ingest menambahkan header `Siaga-Fetched-At` (waktu ambil, sama dengan `meta.fetched_at`) ke setiap `raw.*`; geo-processor mencatat `siaga.pipeline.latency` (ambil → selesai diproses) dan `siaga.geo.queue.duration` (simpan di stream → mulai diproses). Latensi sampai notifikasi (T1 penuh) menyusul saat alert-engine dan notifier ada; trace sudah menyambung sampai `hazard.*`.
7. **Ringkasan query berkardinalitas rendah.** Span query bernama `<OPERASI> <tabel berschema pertama>` (misal `SELECT hazard.event`), dengan teks SQL di `db.query.text` (SQL adapter berupa konstanta tanpa nilai parameter; argumen tidak pernah direkam). Histogram `db.client.operation.duration` per ringkasan menjadi panel query lambat.
8. **Grafana lokal dengan `grafana/otel-lgtm`.** Profil Compose `obs` (`make obs-up`) menjalankan image all-in-one Grafana, Prometheus, Tempo, Loki, dan OTel Collector (~1 GB RAM, jadi tidak ikut `make up`). Grafana di `127.0.0.1:3300` (3000 disisakan untuk web Next.js), OTLP/HTTP di `127.0.0.1:4318`. Dashboard "SIAGA — Pipa data" disimpan sebagai JSON di `deploy/observability/grafana/dashboards/` dan di-provision otomatis, dengan variabel sumber data supaya file yang sama bisa diimpor ke Grafana Cloud. Setiap query dashboard diuji terhadap Prometheus 3.14, Tempo 3.0, dan Loki 3.7 (versi di image) dengan data dari ingest dan geo-processor sungguhan.
9. **Grafana Cloud tanpa perubahan kode.** Cukup `OTEL_EXPORTER_OTLP_ENDPOINT` dan `OTEL_EXPORTER_OTLP_HEADERS` (docs/setup/grafana-cloud.md). Di cluster, layanan mengirim ke OTel Collector yang meneruskan ke Grafana Cloud (fase 1e-2b), sesuai rekomendasi Grafana untuk produksi.

## Konsekuensi

- Modul `libs/go/platform`, `services/ingest`, dan `services/geo-processor` menambah dependensi OpenTelemetry (otel, sdk, exporter OTLP/HTTP, `bridges/otelslog`, `instrumentation/runtime`) beserta turunan gRPC dan `grpc-gateway` yang dibawa exporter; semua modul OpenTelemetry v1.46.0 / log v0.22.0.
- `make ingest` dan `make geo` tidak berubah; telemetri aktif begitu `OTEL_EXPORTER_OTLP_ENDPOINT` diisi di `.env`. Test tidak bergantung pada collector: exporter diuji dengan server OTLP tiruan, span dengan perekam dalam memori.
- Migrasi 00006 menambah kolom nullable; baris outbox lama dan pesan tanpa span tetap valid.
- Uji lokal dengan 10 konektor dan 8 consumer menghasilkan sekitar 1.000 seri metrik aktif, jauh di bawah batas free tier Grafana Cloud. Trace sapuan prakiraan (satu span per kode) paling banyak; sampling `parentbased_traceidratio` bisa dipakai tanpa memecah trace gempa.
- Ekspor langsung dari SDK ke Grafana Cloud hanya untuk laptop; pengiriman tidak diulang lama bila jaringan putus. Produksi memakai OTel Collector (fase 1e-2b).
- Metrik server NATS (endpoint monitoring `/varz`, `/jsz`) dan Garage (`/metrics`) belum dikumpulkan; antrean dan isi stream sudah terlihat dari sisi klien. Dikumpulkan OTel Collector di cluster pada fase 1e-2b.
